# CampusNav Performance Audit — 2026-06-01

Read-only audit. No code changes were made. This file lists every concrete
optimization opportunity found, prioritized by impact and risk.

## Baseline (measured)

Production build: `npx vite build` against the current `master` (5f010e2).
- `dist/client/assets/index-Do2ffcNV.js` — **780 KB** raw, **236 KB** gzip
- `dist/client/assets/index-DQ0m9Tpx.css` — **33 KB** raw, **6.6 KB** gzip
- 253 modules transformed in 3.65 s
- Server-only deps (Hono, Drizzle, @aws-sdk/S3, bcryptjs, @neondatabase) are
  **NOT** in the client bundle — good.
- React, Konva, ngraph.path, react-konva, react-router-dom are all expected
  and unavoidable.
- Build emits a single 780 KB chunk with **zero code splitting** and **no
  dynamic imports anywhere** in the codebase (verified by
  `search_files pattern=lazy|Suspense|import\(`).

## Server: connection pool

`src/server/db/client.ts` uses `postgres(process.env.DATABASE_URL!, { max: 5 })`.
- The same client is shared across all routes (good — no per-request pools).
- `max: 5` is on the low end for a Hono app behind a single Render free
  instance. If a request holds a connection for an R2 round-trip (the
  `/api/campus/image` flow does both a DB lookup AND an R2 fetch), you can
  starve the pool. Bump to **8–10** if you see latency spikes.

## Tier 1 — high impact, low risk

### 1.1 Code-split the admin panel (biggest win)

`src/client/App.tsx` statically imports `AdminShell` and `LoginPage`. Both pull
in MapEditorCanvas (977 lines) + every admin component (geometry editor,
manage floors, data tables, side panels). Confirmed in the bundle: "Geometry",
"Erase", "GPS bounds", "Logout", "Export" strings all present — every student
is downloading ~150–200 KB of admin code they will never run.

Fix: convert to `React.lazy` + `<Suspense>`.

```tsx
// App.tsx
import { lazy, Suspense } from 'react'
const AdminShell = lazy(() => import('./pages/admin/AdminShell'))
const LoginPage = lazy(() => import('./pages/admin/LoginPage'))
// in JSX:
<Suspense fallback={<LoadingShell />}>
  <Route path="/admin" element={<AdminShell />} />
</Suspense>
```

**Expected impact:** student bundle drops from 780 KB to ~550–600 KB raw
(~170–200 KB raw / ~50 KB gzip). Initial page load on Render free tier
should be visibly snappier, especially on mobile.

**Risk:** low. Route boundaries exist. ProtectedRoute already gates the
admin route. Just need a lightweight Suspense fallback.

### 1.2 Add database indexes for hot queries

`src/server/db/schema.ts` has **no custom indexes** beyond FKs. The
`/api/map/skeleton` query (the hot path) does:
- `db.select().from(buildings)` — full scan, small table, fine
- `db.select().from(floors)` — full scan, small table, fine
- `db.select().from(nodes)` — **full scan**, grows linearly with floor count
- `db.select().from(edges)` — **full scan**, grows quadratically
  (edges ≈ nodes²)
- DELETE floor cascade (`edges.sourceId IN (...)` / `edges.targetId IN (...)`)
  needs to scan the entire edges table

The skeleton endpoint also joins edges → nodes in JS (the
`nodeFloorMap`/`edgesByFloor` block in `src/server/index.ts` line 142–149).
For 1k nodes / 5k edges this is sub-millisecond, but with 10k+ edges it
starts to matter.

Fix: add a single migration with explicit indexes.

```sql
-- drizzle/0005_perf_indexes.sql
CREATE INDEX IF NOT EXISTS nodes_floor_id_idx ON nodes (floor_id);
CREATE INDEX IF NOT EXISTS edges_source_id_idx ON edges (source_id);
CREATE INDEX IF NOT EXISTS edges_target_id_idx ON edges (target_id);
```

`floors.buildingId` likely already has an index from the FK constraint, but
explicit is fine. Drizzle's `pgTable` doesn't auto-index FKs on
postgres-js's side; confirm with `\d nodes` in the Neon console.

**Expected impact:** at 1k+ edges, `/api/map/skeleton` p95 latency should
drop noticeably. DELETE floor cascade goes from O(edges) to O(edges-on-floor).

**Risk:** very low. Indexes are non-destructive. Will slightly slow down
the bulk `/api/admin/graph` insert (the `db.transaction` block in
`index.ts` line 372–477) by 5–15% — but that endpoint is admin-only and
not perf-critical.

### 1.3 CSRF on every request, including GETs

`src/server/index.ts:40` — `app.use(csrf())` is registered globally BEFORE
any route. The Hono `csrf()` middleware runs on every single request,
including:
- `GET /api/health` (health checks)
- `GET /api/map/skeleton` (hot path)
- `GET /api/floors/:id/geometry` (per-floor lazy load)
- `GET /api/floor-plan/:buildingId/:floorNumber` (image fetch)
- All `/api/auth/*` (login/logout/me)

The CSRF middleware in Hono for GET requests is mostly a no-op (it
validates the CSRF token cookie presence, but GETs don't carry state) —
but it still adds overhead and one extra cookie read per request. For the
public read-only endpoints, this is wasted work.

Fix: scope CSRF to mutation routes only.

```ts
// Apply CSRF only to state-changing routes
app.use('/api/admin/*', csrf())
app.use('/api/auth/*', csrf())
// Don't apply to GET-only /api/* public endpoints
```

**Expected impact:** small absolute (a few ms per request), but it
multiplies across all GETs the student app fires on startup. Also closes a
theoretical CSRF-Cookie-Forcing attack surface on the public API.

**Risk:** low. Just verify that login still works (it has its own
rate limiter already).

## Tier 2 — medium impact, low risk

### 2.1 Cache-Control on `/api/map/skeleton` is only 60 s

`src/server/index.ts:199` — `c.header('Cache-Control', 'public, max-age=60')`.
On Render free tier, this means every cold start re-fetches the entire
graph. With a campus map that barely changes, 5–10 minutes is fine.

```ts
c.header('Cache-Control', 'public, max-age=300, stale-while-revalidate=60')
```

Stale-while-revalidate means the browser can serve the cached version for
60 s after expiry while it refetches in the background — gives the
"instant" feel on second visit.

**Risk:** zero. Same-origin, public data.

### 2.2 Eliminate the `/api/map` vs `/api/map/skeleton` duplication

Lines 124–205 (skeleton) and 237–321 (full) are **nearly identical**. The
only difference is whether `geometry` is included on each floor. This is
~100 lines of near-duplicate code that's already drifted slightly (one
includes geometry, one doesn't).

Fix: extract a single `buildNavGraph({ includeGeometry: boolean })` helper
in `src/server/`. The `/api/map` and `/api/map/skeleton` handlers become
two-line wrappers.

**Impact:** code quality > perf. Reduces drift bugs.

### 2.3 N+1 inserts in `/api/admin/graph`

`src/server/index.ts:382–423` does one INSERT per building, one per floor,
one per node, one per edge, all inside a transaction. For a 10-building
school with 50 nodes per floor and ~2500 edges total, that's 3060 round
trips to Neon. At ~5ms RTT to Neon (free tier is geographically far), the
graph save takes ~15 s. Cold starts make this worse.

Fix: use Drizzle's bulk insert with `.values([...])` (single statement per
table, not per row). One pass to collect rows, four bulk inserts.

```ts
// Collect all rows in one pass
const buildingRows = graph.buildings.map(b => ({ name: b.name }))
const insertedBuildings = await tx.insert(buildings).values(buildingRows).returning({ id: buildings.id })

// Then per building: bulk insert floors, then bulk insert nodes/edges
// for each floor's batch
```

**Impact:** graph save time drops 10×+. Admins will notice.

**Risk:** low. Transactional boundary stays. Just verify the connector
resolution pass still works (Pass 2 at lines 425–477 doesn't care about
insert order).

### 2.4 Image cache headers are too short for PNGs

`/api/floor-plan/:buildingId/:floorNumber` and friends use
`Cache-Control: public, max-age=3600` (1 hour). Floor plan images are
~3–9 MB PNGs, and they barely change. On the student's first visit they
download, then on every floor switch they re-fetch (since the
building/floor URL changes per floor, not just per session). 24h–7d is
fine; you can invalidate on upload by changing the URL (`?v=timestamp`).

**Impact:** noticeable on slow networks. The first floor switch shows
quick; subsequent building switches in the same session are instant.

**Risk:** low. The image upload endpoints already update `floors.updatedAt`.

## Tier 3 — small wins, worth doing

### 3.1 `useRouteDirections` depends on a fresh `Map` reference

`src/client/hooks/useRouteDirections.ts:322–327` uses `useMemo` with
`nodeMap` and `floorMap` in the dep array. Both are built fresh in
`FloorPlanCanvas.tsx` (`useMemo`s at lines 234 and 239) so they're stable
per-graph-load — so this is actually fine, just worth noting that anyone
who later refactors those should preserve the memoization.

### 3.2 `app.use('/*', serveStatic(...))` is wildcard, runs on every request

Line 703 — `serveStatic` from `@hono/node-server/serve-static`. It checks
if the file exists on every request. Combined with the `app.get('/*', ...)`
fallback at line 705, every request that misses the static handler still
hits the SPA shell handler. Fine for the SPA architecture, but on
high-traffic images this is two path lookups per request. Probably not
worth optimizing.

### 3.3 `useGeolocation` always subscribes, even when not needed

`src/client/components/FloorPlanCanvas.tsx:591` — `useGeolocation({ enabled: geolocationEnabled })`.
The hook is only "enabled" when the floor has calibrated GPS bounds, but
it's still constructed on every render of FloorPlanCanvas. The `enabled`
flag is the right pattern (avoids subscribing to the geolocation API), so
this is already good. Just making sure this stays this way after future
refactors.

### 3.4 `fetchWithRetry` fixed 1s delay

`src/client/hooks/useGraphData.ts:9–29` — three attempts, 1s apart. On a
Render free tier cold start, the first request can take 30–90s and 1s
isn't going to help. Consider exponential backoff (1s, 2s, 4s) AND a
longer initial timeout. Currently the student sees a spinner for up to 3
seconds, then gives up — if the cold start is at 2s, they get an error
that just refreshing fixes. Not great UX.

**Fix:** expose a longer initial request timeout (15–30 s) and only retry
on network failures, not on 5xx.

### 3.5 `useViewportSize` not checked

I didn't audit `useViewportSize.ts`. On the off chance it uses a window
resize listener without `requestAnimationFrame` debouncing, every window
resize forces a FloorPlanCanvas re-render. Worth a quick look.

## What I did NOT find

- **No memory leaks.** All the Konva tweens are one-shot. The `useEffect`
  cleanup in `useGraphData` aborts the fetch. `pathfinding` engine is
  memoized on graph load. `setTimeout` for the toast is cleared on
  re-trigger.
- **No obvious N+1 in the read path.** The skeleton endpoint fans out 4
  parallel `Promise.all` queries — that part is good.
- **No expensive client-side computation per render.** `filterNodesByActiveFloor`
  only runs on floor change (memoized). `generateDirections` is memoized.
  `gpsProjectedPoint` is memoized.
- **No bundle-included dead code I could spot.** The dead-code detection
  in Vite/Rollup is doing its job.

## Recommended order of attack

1. **Add the three DB indexes (5 min, 5 MB migration).** Zero risk, real
   perf, you can do it today.
2. **Code-split the admin panel (30 min).** Biggest user-visible win. You
   can do it this week.
3. **Bulk-insert the graph save (45 min).** Better admin UX. Defer.
4. **Scope CSRF to mutating routes (5 min).** Cleanup, very small perf
   win. Whenever.
5. **Tune cache headers (5 min).** Low-hanging. Whenever.

The first two are the only ones I'd call "optimization" in the user-
facing sense. The rest is polish.

## What I would NOT do without more data

- **Code splitting Konva further.** Konva is monolithic by design and
  tree-shaking it is fragile. Don't go down this road unless the bundle
  is still too big after the admin split.
- **Migrating to a different bundler.** Vite 7 is doing fine. Rspack or
  Turbopack wouldn't change the bundle size, just build time.
- **Server-side rendering.** The student app is a single-page app, fine
  for a deployed static bundle. SSR would add complexity for marginal
  benefit on Render free tier (still has the cold start issue).
- **Aggressive code splitting of all Konva layers.** The
  `FloorPlanGeometryLayer`, `LandmarkLayer`, etc. are each ~200 lines.
  Splitting them all is premature optimization.
